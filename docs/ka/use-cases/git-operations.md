# Git ოპერაციები

SupportTools მართავს ბევრ პროექტს, რომელთაგან თითოეული შეიძლება
შედგებოდეს რამდენიმე Git რეპოზიტორიისგან. აქ მოცემული ბრძანებები
საშუალებას გაძლევენ შეუნახოთ ყველა ეს რეპო სინქრონიზებული, ხელით
თითო ფოლდერში გადასვლის გარეშე.

ყველა ბრძანება ვარაუდობს, რომ თითოეულ პროექტს აქვს Git რეპოზიტორიების
URL-ები კონფიგურირებული პროექტის `Git` ქვემენიუს მეშვეობით (იხ.
[კონფიგურაცია](../configuration.md)).

## როგორ მუშაობს სინქი

ყველა სინქის ბრძანება იყენებს ერთნაირ ხუთნაბიჯიან pipeline-ს
თითოეულ რეპოზე:

1. **Clone** — `git clone <url> <path>` თუ ფოლდერი არ არსებობს
2. **Stage და ინსპექცია** — `git add .`, შემდეგ `git status --porcelain`
3. **Commit** — თუ არის დაუკომიტებელი ცვლილებები, ეკითხება მესიჯს და
უშვებს `git commit`-ს; batch-ში ასევე ეკითხება, გამოიყენოს თუ არა
იგივე მესიჯი დანარჩენი რეპოებისთვის
4. **Pull** — `git pull` თუ remote-ში ახალი commit-ებია
5. **Push** — `git push` თუ ლოკალურს აქვს commit-ები, რომლებიც remote-ში
არ არის

პროცესორი ანაწილებს თითოეულ რეპოს ოთხ მდგომარეობაში merge-base-ის
მეშვეობით: `UpToDate`, `NeedToPull`, `NeedToPush`, ან `Diverged`.
`Diverged` რეპოზე სრულდება იგივე `git pull`, რაც `NeedToPull`-ზე (Git
ცვლილებებს აერთიანებს merge-ით ან rebase-ით, `pull.rebase` პარამეტრის
მიხედვით), შემდეგ კი შედეგი push-ით იგზავნება; რეპო შეცდომით ჩერდება
მხოლოდ მაშინ, თუ ეს pull ჩავარდა, მაგალითად merge კონფლიქტის დროს.

## თუ გჭირდება ყველა რეპოს ერთბაშად სინქი

გამოიყენე როცა დიდხანს არ ხართ კონტაქტში და გინდა ყველა პროექტი
განახლებული იყოს.

**ნაბიჯები**

1. `Main Menu` → `Sync All Projects All Gits V2`
2. თუ ზოგი პროექტი `remote`-ია (ამ კომპიუტერზე არ არის, იხ.
[ქვემოთ](#თუ-პროექტი-ამ-კომპიუტერზე-ჯერ-არ-არის)), უპასუხე კითხვას
`Include N remote-only projects (their gits will be cloned to this computer)?`.
ნაგულისხმევი `n` მხოლოდ ლოკალურ პროექტებს ასინქრონებს; `y` remote
პროექტებსაც დაკლონავს, როგორც ადრე ყოველი სინქი აკეთებდა.
3. შეიყვანე commit მესიჯი (გამოიყენება ლოკალური ცვლილებების მქონე
რეპოებისთვის)

**მოსალოდნელი შედეგი**

* თითოეული რეპო აცხადებს დასაწყის და საბოლოო მდგომარეობას
* ცვლილებების გარეშე რეპოები მთავრდება მყისიერად
* diverged ისტორიის რეპოებზე იწერება `Diverged` გაფრთხილება, შემდეგ
სრულდება pull და push; შეცდომით ჩერდება მხოლოდ ის რეპო, რომლის pull
ჩავარდა (მაგ. merge კონფლიქტი), და მას ხელით გადაწყვეტა სჭირდება

**ხშირი შეცდომები**

* **Diverged branch-ები.** თუ რეპოს აქვს ლოკალური და remote
commit-ები ერთდროულად, ხელსაწყო უშვებს `git pull`-ს, რომელიც
ცვლილებებს აერთიანებს merge-ით ან rebase-ით (Git-ის `pull.rebase`
პარამეტრის მიხედვით), შემდეგ კი აკეთებს push-ს. თუ pull ჩავარდა
(მაგალითად, merge კონფლიქტის გამო), ეს რეპო შეცდომით ჩერდება —
გადაწყვიტე ხელით ხელახალი გაშვების წინ.
* **არ არის ჩაკეტვა რეპოებს შორის.** თუ ორი სინქის გაშვება გადაიფარება
(მაგ. ორი shell), ერთი URL-ის რეპოები შეიძლება დააფრქვან. არ
გაუშვა სინქი ერთდროულად.
* **გამეორებული commit მესიჯი.** პირველი მესიჯის შემდეგ ხელსაწყო
გეკითხება `Use this message for next commits?`. `y` — მესიჯი
გავრცელდება batch-ის ყველა დანარჩენ რეპოზე; `n` — მომდევნო commit-ზე
მესიჯს ისევ გკითხავს და ნაგულისხმევად წინა მესიჯს შემოგთავაზებს.
* **ჩუმი auth ჩავარდნა.** ხელსაწყო ეყრდნობა OS-ის Git credentials-ს
(SSH key, credential manager). თუ auth ჩავარდა, output არის ზოგადი
"cannot clone/push" — ჯერ შეამოწმე `git push` ხელით ხელსაწყოს გარეთ.

## თუ გჭირდება ერთი ჯგუფის რეპოების სინქი

გამოიყენე როცა ერთი გუნდი ან პროდუქტი იყო აქტიური და გინდა მხოლოდ
ის არეალი განახლდეს.

**ნაბიჯები**

1. `Main Menu` → `Project Groups List` → (აარჩიე ჯგუფი) → `Sync One Group All Projects Gits V2`
2. როგორც სრულ სინქში, ჯგუფის `remote` პროექტები მხოლოდ მაშინ
დაიკლონება, თუ მათ შესახებ კითხვას `y`-ით უპასუხებ.

**მოსალოდნელი შედეგი**

* იგივე პერ-რეპო ანგარიში, რაც სრულ სინქში, ოღონდ შეზღუდული არჩეული
ჯგუფის პროექტებით

**ხშირი შეცდომები**

* **ჯგუფთაშორისი დამოკიდებულებები.** თუ ჯგუფის პროექტი დამოკიდებულია
სხვა ჯგუფის გაზიარებულ კოდზე, მხოლოდ ერთი ჯგუფის სინქი დაგვტოვებთ
მოძველებული საერთო კოდით. ეჭვის შემთხვევაში სრული Sync უფრო უსაფრთხოა.

## თუ პროექტი ამ კომპიუტერზე ჯერ არ არის

რეესტრის სინქრონიზაციის შემდეგ ყველა კომპიუტერზე ყველა პროექტი ჩანს,
ფიზიკურად კი თითოეული მხოლოდ ზოგიერთ კომპიუტერზეა. პროექტი `local`-ია,
თუ მისი `ProjectFolderName` ამ კომპიუტერზე არსებობს, თორემ `remote`.
პროექტების სიაში ნიშანი ყოველი პროექტის გვერდით ჩანს
(`MyProject (remote)`), ყოველ ჯგუფს კი უწერია `local: N, remote: N`.
`Support Tools Parameters Editor`-ის `HideRemoteOnlyProjects` remote
პროექტებს სიებიდან მალავს.

ჯგუფური ბრძანებები ნაგულისხმევად ლოკალურ პროექტებზე მუშაობს:

* `Sync All Projects All Gits V2`, `Sync One Group All Projects Gits V2`,
`Update Outdated Packages` და `Distribute all packages` გეკითხება,
ჩაირთოს თუ არა remote პროექტებიც (ნაგულისხმევად `n`), რადგან მათი
სინქრონიზაცია მათ აქ დაკლონავს;
* `Check all projects build`, `Check group projects build`,
`Clear All Groups All Solutions All Projects`,
`Reverse Package Distribution`, `Remove Unused Package Versions` და
`Open all projects By Visual Studio` remote პროექტებს ყოველთვის
ტოვებს და წერს, რამდენი გამოტოვა: ფაილების გარეშე ისინი მხოლოდ იმას
დაწერდნენ, რომ ფოლდერები არ არსებობს.

**ნაბიჯები**

1. `Main Menu` → `Project Groups List` → (ჯგუფი) → `Projects List` →
(`remote` პროექტი) → `Clone Project To This Computer` (ჩანს მხოლოდ
remote პროექტებისთვის)
2. თუ პროექტს scaffold seeder რეპოები აქვს, უპასუხე, დაიკლონოს თუ არა
ისინიც (ნაგულისხმევად `n`)
3. დაადასტურე `Clone N gits of project ... to <folder>?`

**რას აკეთებს**

1. ქმნის `ProjectFolderName`-ს.
2. პროექტის ყოველი რეპოსთვის, რომლის ჩანაწერიც `GitProjects`-ში არ
არის, უშვებს `Update Git Projects`-ის სკანირებას მხოლოდ ამ რეპოსთვის და
ინახავს. ეს კლონამდე ხდება: რეპოს, რომლის ფოლდერის სახელიც
`{SpaProjectFolderRelativePath}`-ით იწყება, ფოლდერის დასადგენად პროექტის
`SpaProjectName`-ის `GitProjects` ჩანაწერი სჭირდება.
3. ყველა რეპოს კლონავს იმავე მექანიზმით, რასაც V2 სინქი იყენებს.
4. ამოწმებს შაბლონების ფაილებს: ყოველი რეპოს `.gitignore` შაბლონი და
პროექტის `.editorconfig` შაბლონი არსებობს და დაკლონილი ფაილები მათ
ემთხვევა.
5. ამოწმებს პროექტის საიდუმლო ფაილებს (მისი server info-ების
`AppSettingsJsonSourceFileName`, `SeedProjectParametersFilePath`,
`PrepareProdCopyDatabaseProjectParametersFilePath`,
`PairedDbObjectsResultFileName`). თუ რომელიმე აკლია, ჩამოთვლის მათ და
გთავაზობს `Sync Registry With SupportToolsServer...`-ის გაშვებას,
რომელიც მათ ჩამოიტანს, შემდეგ კი ისევ ამოწმებს.
6. წერს ანგარიშს: ფოლდერი, განახლებული `GitProjects`, რამდენი რეპო
დაიკლონა და რომელი არა, შაბლონების პრობლემები და დაკარგული ფაილები.

**ხშირი შეცდომები**

* **ნაწილობრივი კლონი.** ფოლდერი პირველ რიგში იქმნება, ამიტომ
ჩავარდნილი კლონის შემდეგაც პროექტი უკვე `local`-ად ითვლება. გაასწორე
მიზეზი (იხ. ანგარიში) და პროექტზე გაუშვი
`Sync One Project All Gits With Scaffold Seeders V2`.
* **`GitProjects has no X (SpaProjectName of project Y)`.** სკანირებამ
`SpaProjectName`-ის სახელის პროექტი ვერ იპოვა. შეამოწმე სახელი, ან Gits
სიიდან გაუშვი `Update Git Projects` (ან
`Update Git Projects From SupportToolsServer`). V2 სინქიც იმავე შეცდომას
წერს exception-ით გაჩერების ნაცვლად, პროექტის დანარჩენი რეპოები კი
მაინც სინქდება.

## თუ git პროექტები კლონირების გარეშე გჭირდება

`GitProjects` ყოველ git რეპოს მასში არსებულ `.csproj` / `.esproj`
ფაილებთან აკავშირებს, მათი დამოკიდებულებებით; მას V2 სინქი და პაკეტების
ბრძანებები იყენებს. ყოველი კომპიუტერი მას თვითონ ითვლის და ის არასოდეს
სინქრონიზდება. ორივე ბრძანება `Support Tools Parameters Editor` → `Gits`-შია:

* `Update Git Projects` ლოკალურ კლონებს ასკანირებს;
* `Update Git Projects From SupportToolsServer` იმავე ჩანაწერებს
SupportToolsServer-იდან იღებს, რომელიც ყოველი რეპოს თავის კლონებს
ასკანირებს, ამიტომ ახალ კომპიუტერს კლონირება არ სჭირდება. ის მთელ
`GitProjects`-ს ცვლის და ბეჭდავს, რამდენი ჩანაწერი დაემატა, შეიცვალა და
წაიშალა. სერვერის ცარიელი სია (სერვერს ჯერ არ დაუსკანირებია) ან სერვერის
შეცდომა არაფერს ცვლის.

თუ პროექტის სახელი ორ რეპოშია, იმარჯვებს რეპო, რომელიც სახელების რიგით
უფრო გვიანაა, როგორც ლოკალურ სკანირებაში, და სახელი გაფრთხილებით ჩანს.

## თუ git რეპოები სხვა კომპიუტერებზე გჭირდება

git რეპოების სია (`Gits`) ცენტრალური რეესტრის ნაწილია (იხ.
[კონფიგურაცია](../configuration.md#ცენტრალური-რეესტრი-supporttoolsserver)):
`Sync Registry With SupportToolsServer...` და ავტომატური სინქრონიზაცია მას
დანარჩენთან ერთად ატარებს. `Support Tools Parameters Editor` → `Gits` →
`Sync Gits With SupportToolsServer...` იმავე სინქრონიზაციას მხოლოდ git
რეპოებზე უშვებს.

რეპოს `.gitignore` შაბლონი სერვერზე რეპომდე უნდა იყოს: ჯერ
`Git Ignore Patterns` დაასინქრონე, ან გამოიყენე სრული სინქრონიზაცია,
რომელიც შაბლონებს პირველად აგზავნის. SupportToolsServer ყოველ მიღებულ
რეპოს აკლონირებს (`Update Git Projects From SupportToolsServer`-ისთვის).

## თუ გჭირდება პროექტზე რეპოს დამატება, ნახვა ან წაშლა

გამოიყენე ახალი პროექტის bootstrap-ისთვის ან ახალი რეპოს onboarding-ისთვის.

**ნაბიჯები**

1. `Main Menu` → `Project Groups List` → (ჯგუფი) → `Projects List` →
(პროექტი) → `Git` ქვემენიუ
2. ქვემენიუდან აარჩიე `New Git` დასამატებლად, ან არსებული ჩანაწერი
წაშლა/რედაქტირებისთვის

**რას სთავაზობს ქვემენიუ**

* Git clone ფაილების load და save (რეპოს სიის export/import)
* ახალი Git ჩანაწერის დამატება (URL, ლოკალური ფოლდერის სახელი, branch
ინფო)
* პერ-რეპო ქმედებები თითოეულ უკვე რეგისტრირებულ ჩანაწერზე

**ხშირი შეცდომები**

* **URL შეუსაბამობა.** თუ ცვლი რეპოს remote URL-ს ამ ქვემენიუში, მაგრამ
ლოკალური ფოლდერი უკვე სხვა remote-ზე იყურება, სინქი აღმოაჩენს
შეუსაბამობას და გაჩერდება. ან წაშალე ლოკალური ფოლდერი ხელით ან
განაახლე remote URL არსებულ checkout-ში.
* **ფოლდერის შეჯახება.** ორი ჩანაწერი, რომელიც ერთსა და იმავე
ლოკალურ ფოლდერზე იყურება, ერთმანეთს დააფარავს clone-ის დროს. ხელსაწყო
ვერ აღმოაჩენს ამას — ფოლდერების სახელები განცალკევებული შეინახე.

გამოიყენე შენი ჩვეულებრივი Git კლიენტი.
