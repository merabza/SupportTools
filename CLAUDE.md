# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SupportTools is a .NET 10 menu-driven console application that orchestrates Git sync, database lifecycle, deployment, project scaffolding, and remote-server operations across a fleet of related .NET projects. Remote work goes through a companion HTTP service called **WebAgent**; all persistent state lives in a single JSON parameters file under the user profile.

Detailed docs live in [docs/en/](docs/en/) — `architecture.md`, `configuration.md`, `development.md`, `getting-started.md`, and `use-cases/`. Prefer reading those over re-deriving facts from the code.

## Build / run

```bash
dotnet build SupportTools.slnx
dotnet run --project SupportTools/SupportTools.csproj
```

Unit tests live in `SupportTools.Tests` (xUnit + Moq; `dotnet test SupportTools.slnx`). Coverage is thin — only a few menu commands — so verification is still mostly manual: build + run + exercise the menu. `Inputer` prompts read the console directly (`Console.ReadKey`) and fail in the test host; to test an interactive command, give it an internal constructor that takes the input functions, as `SaveGitIgnoreAsNewTemplateCliMenuCommand` does (`SupportTools.csproj` already has `InternalsVisibleTo` for the test project). A test class that redirects `Console.Out` must be marked `[Collection(ConsoleCaptureCollection.Name)]` — `Console.SetOut` is process-wide and xUnit runs classes in parallel, so without it console-capturing classes race each other. Commands that start external tools take them the same way (an internal constructor with the step: Visual Studio in `OpenAllProjectsByVisualStudioCliMenuCommand`, the csproj edits of `ReversePackageDistributionCliMenuCommand` and `PackageDistributor`, the pack and upload of `PackageBuilder`, the git steps of `CloneProjectToThisComputerCliMenuCommand`, the git/build/pack/upload/distribution steps of `DistributeAllPackagesCliMenuCommand` behind `IPackageDistributionSteps`), so a test or a mutant never starts devenv, a build or an upload, or changes a real project. Tests that need the real git use `GitTestRepositories` (throwaway bare remotes under `%TEMP%`, local paths, no network); `CliMenuTestAccess` reaches the protected `RunBody` / `GetActionDescription` and the private `askRunAction` flag. Stryker.NET mutates only a project that the test project references directly, which is why `SupportTools.Tests` references `LibTools` too. `stryker-report/` holds git-ignored Stryker mutation-report output; no Stryker config is checked in.

## Critical: sibling-repo layout

`SupportTools.slnx` references **eight external repos as siblings** via relative paths (`../AppCliTools/...`, `../SystemTools/...`, etc.). The build fails immediately if those checkouts are not present alongside this repo. See [docs/en/getting-started.md](docs/en/getting-started.md) for the clone list. The repos are:

`AppCliTools`, `ConnectionTools`, `DatabaseTools`, `ParametersManagement`, `SupportToolsServerShared`, `SystemTools`, `ToolsManagement`, `WebAgentContracts`.

If a referenced type can't be found, first check whether the sibling repo exists and is on the right branch — don't assume it's a missing using.

## Build is strict — every warning is an error

`Directory.Build.props` sets `TreatWarningsAsErrors=true`, `CodeAnalysisTreatWarningsAsErrors=true`, `EnforceCodeStyleInBuild=true`, `AnalysisMode=All`, plus `SonarAnalyzer.CSharp` globally. There are **no per-project overrides**. Any analyzer warning, style violation, or nullable-reference warning fails the build. Compiler-implicit usings are **disabled** — every file declares its own `using`s.

Local suppressions use `// ReSharper disable once <rule>` rather than global config. Primary constructors are avoided (look for `// ReSharper disable once ConvertToPrimaryConstructor`). Service classes are `sealed` where practical.

## Package versioning

Central via `Directory.Packages.props` (`ManagePackageVersionsCentrally=true`). `.csproj` files use `<PackageReference Include="X" />` with **no version**. To add a package: add `<PackageVersion ... Version="..."/>` to `Directory.Packages.props` *first*, then `<PackageReference Include="..."/>` in the consuming project.

## Architecture in one paragraph

Five layers, bottom-up: (1) data models in `SupportToolsData`/`LibGitData`/`LibTools`; (2) process orchestration in `LibDotnetWork`/`LibGitWork`/`LibNpmWork`; (3) domain logic in `LibDatabaseWork`/`LibCodeGenerator`/`LibAppInstallWork`/`LibSupportToolsServerWork`; (4) high-level workflows in `LibAppProjectCreator`; (5) entry point in `SupportTools` (console), with DI registration in `SupportTools/DependencyInjection/SupportToolsServices.cs`. Menu commands are factory-strategy classes auto-discovered through `AddTransientAllStrategies<>` at startup.

## Adding work — the two main patterns

**New menu command:** create `*CliMenuCommandFactoryStrategy` + `*CliMenuCommand` under `SupportTools/Menu/<level>/`, then register the strategy name in the matching list in [SupportTools/Menu/MenuData.cs](SupportTools/Menu/MenuData.cs) (`MainMenu*`, `ProjectGroupSubMenu*`, or `ProjectSubMenu*`). DI picks it up automatically.

**New per-project tool action:** add an enum value to [SupportToolsData/EProjectTools.cs](SupportToolsData/EProjectTools.cs) or [EProjectServerTools.cs](SupportToolsData/EProjectServerTools.cs) (with a Georgian-language comment matching existing style), implement a `*ToolAction` in the right `Lib*` library, and wire it via [SupportTools/ToolCommandFactory.cs](SupportTools/ToolCommandFactory.cs). The factory looks up strategies by `tool.ToString()`, so the strategy's `ToolCommandName` must equal the enum name.

## State and config

All registered projects, servers, git repos, templates, API clients, and connection strings live in one JSON file at a user-profile path supplied by the `--use` argument and loaded by `ParametersService<SupportToolsParameters>`. Top-level shape is `SupportToolsParameters` ([SupportToolsData/Models/SupportToolsParameters.cs](SupportToolsData/Models/SupportToolsParameters.cs)). `Newtonsoft.Json` is used so adding new fields to a model is safe — existing JSON loads fine.

When editing fields: add property → add a `FieldEditor` under `SupportTools/FieldEditors/` → wire into the corresponding `*ParametersEditor` in `SupportTools/ParametersEditors/` or `Cruders/`. Direct JSON edits skip in-app validation.

Every change must end with `IParametersManager.Save` of the **root** object (`parametersManager.Parameters`). Passing a sub-object (e.g. `AppProjectCreatorAllParameters`) overwrites the whole file with it and replaces `IParametersManager.Parameters`, which breaks every later `(SupportToolsParameters)` cast. Cruders built on `SimpleNamesListCruder` / `SimpleNamesWithDescriptionsCruder` (AppCliTools) save only when constructed through their `IParametersManager` overload; the old overloads stay for other applications and save nothing. `ParametersManager.Save` replaces the file atomically (temp file in the same folder + `File.Move`), skips the write when the content is unchanged, and keeps the 10 newest `<file>.yyyyMMdd-HHmmss-fff.bak` copies next to it; manually named backups are never deleted. The `IParametersManager` of DI is the auto-sync decorator `AutoSyncParametersManager` around `SupportToolsMainParametersManager` (see Registry auto-sync): it returns the same `Parameters` object, so the casts are unchanged.

## Machine profile and path mapping (central registry)

SupportTools runs on more than one computer: **PAZISI** is the main Windows computer (its folder layout is the canonical one) and **Merinson** is a separate Linux computer that also runs SupportTools. Both had `IsLocal=true` in `Servers` because the file was copied between them; `IsLocal` is per computer and is no longer meant to be shared.

- Machine fields on `SupportToolsParameters`: `MachineName` (optional, read it via `GetMachineNameOrDefault()` → `Environment.MachineName`; `MachineNameFieldEditor` stores null when the offered name of this computer is accepted, so a copied file keeps working), `CurrentMachineServerName` (the `Servers` key that is this computer; null = no such entry; PAZISI on PAZISI, Merinson on Merinson) and `PathMappings` (`List<PathMappingModel { CanonicalPrefix, LocalPrefix }>`). They are edited at the top of "Support Tools Parameters Editor"; the Path Mappings list has "Suggest Path Mappings...", which collects drive + first-folder roots (`D:\1WorkDotnet`) from the README §4.4 path fields (project paths, ServerInfo appsettings, ProjectCreator folders, local FileStorage paths) and asks for a local prefix per root.
- `ServerDataModel.IsLocal` is computed: `Program.cs` calls `ServersIsLocalCalculator.Recalculate` right after the parameters load, before the menu and `--run`. With `CurrentMachineServerName` set, only that server (case-insensitive) is local; when it is empty the stored values stay (old files keep working). The `CurrentMachineServerName` editor recalculates at once, and so does `ServerDataCruder` after adding or renaming a server; while the name is set, the `Servers` editor hides `IsLocal`. Code that replaces `Servers` (registry pull) must call it again.
- Path rule — `LibSupportToolsServerWork/Registry/Paths/PathMapper`: the canonical form is the Windows absolute path as on PAZISI. `ToLocal` / `ToCanonical` swap the longest matching prefix; a prefix matches only on a separator boundary (`D:\1WorkDotnet` ≠ `D:\1WorkDotnetX`), case-insensitively, ignoring trailing separators. On non-Windows (`Path.DirectorySeparatorChar == '/'`) the rest of the path also swaps `\` ↔ `/`. An unmatched path is returned unchanged; on Linux a Windows-rooted path in `ToLocal` or a `/`-rooted path in `ToCanonical` is also added to `Issues` (the sync command shows them). Relative paths (`GitProjectFolderName`) use `NormalizeRelativeToLocal` / `NormalizeRelativeToCanonical` (separators only). null/empty pass through. The internal constructor takes the separator, so tests cover both modes on Windows.
- Fields that never sync are listed in `LibSupportToolsServerWork/Registry/MachineLocalFields.cs`; add every new machine-local field there.

## Registry sync engine (central registry)

`LibSupportToolsServerWork/Registry/Sync/` is the 3-way, per-record sync engine (local / server / last successful sync, with the server's `Version`; plan README §4.3 in SupportToolsServer's `docs/CentralRegistry`). It has no UI and no concrete collections: the adapters (C3/C4), the "Sync Registry" command (C5) and auto-sync (D2) build on it. Tests in `SupportTools.Tests/Registry/Sync/` use `FakeRegistrySyncAdapter`, an in-memory server that follows the version rules below.

- **State**: `SupportToolsParameters.RegistrySyncState` (`RegistrySyncStateModel`, a machine-local field) is saved with the data by the same `Save`. Per collection (`Collections[CollectionName]`): `Records` (key → server `Version` + hash of the local contract at the last successful sync) and `ExcludedKeys` (never pushed or pulled, e.g. a database connection that differs on Linux); plus `LastSyncUtc` (set by an execution that changed data or state) and `ServerAddress` (the SupportToolsServer whose versions the state holds; written by every execution of an engine that has one, see Engine; null in files older than D2). The dictionaries and the set are get-only and created with `OrdinalIgnoreCase`: Newtonsoft fills those instances on load, so keys stay case-insensitive (G8) and the instances are never replaced.
- **Adapter** (`IRegistrySyncAdapter`, one per collection; the contract is the server's `Sts…DataModel`, an opaque `object` to the engine):
  - `CollectionName`: the state key, so never rename it. `Order`: dependency order; a referenced collection has a lower order than the one that references it, and Projects is last.
  - `Normalize(contract)`: `""` → null, sets sorted with `OrdinalIgnoreCase`, etc. It must be idempotent; the engine checks that normalizing again keeps the hash.
  - `GetLocalRecords()`: key → contract with canonical paths and without machine fields. `GetServerRecords(ct)`: key → `RegistryServerRecord(contract, Version)`.
  - `Upsert(key, contract, expectedVersion, ct)` returns `Result<int>` with the new version (expected version 0 = create). `Delete(key, expectedVersion, ct)`. Errors carry the server's code.
  - `ApplyLocal(key, contract)` merges into the local model in place: it keeps machine fields and fields the contract lacks and never replaces dictionary instances. The key is the local spelling when the record exists locally. `RemoveLocal(key)`. Adapters never save.
  - Optional `IRegistryFileSyncAdapter` (C6, StoredFiles: the local records are files): `GetMissingLocalKeys()` (records that belong here but whose file is missing; read after `GetLocalRecords`) and `PrepareApplyLocal(key, contract, ct)` (fetches what the server list lacks, the file content, before `ApplyLocal`). Its deletes always wait for the user (see Planner).
- **Hash** (`RegistryContractHasher`): SHA-256, upper-case hex, of canonical JSON. The root `Version` is removed; nulls and default values are omitted, so a new, still-empty contract field keeps the old hashes; object properties and dictionary keys are sorted ordinally; list order is kept. The serializer settings live only there. Changing them makes every stored hash look locally changed, and a golden-value test guards against that.
- **Planner** (`RegistrySyncPlanner.CreatePlan`, a pure function):
  - A key in `ExcludedKeys` → Skipped.
  - Record on both sides: equal hashes → InSync (also when only one side changed); not in the state → Conflict(FirstSyncDiffers); otherwise localChanged = hash ≠ state.Hash and serverChanged = Version ≠ state.Version decide between InSync / Pull(Update) / Push(Update) / Conflict(BothChanged).
  - Local only: not in the state → Push(Add); unchanged → Pull(Delete); changed → Conflict(DeletedOnServer).
  - Server only: not in the state → Pull(Add); unchanged → Push(Delete); changed → Conflict(DeletedLocally).
  - Only in the state (deleted on both sides) → InSync, and the executor forgets it.
  - File collections (`RegistryCollectionSnapshot.MissingLocalKeys` / `DeletesNeedConfirmation`, set by the engine for an `IRegistryFileSyncAdapter`): a missing local key with a server record → Pull(Add) whatever the state, so a missing file is taken again and never deleted on the server; every Pull(Delete) and Push(Delete) becomes Conflict(DeleteNeedsConfirmation), so only a conflict resolution deletes a file (Apply, Pull only, Push only and D2's presets never do).
  - Plan items are ordered by `Order`, collection and key, and carry the local spelling of the key when the record exists locally.
- **Engine** (`RegistrySyncEngine(adapters, parametersManager)`, optional `ServerAddress`):
  - `CreatePlan(ct)` reads, normalizes and hashes every adapter's records and changes nothing. It fails on a server read error (returned unchanged, e.g. `ApiRequestFailed` when offline), on keys that differ only by case (`DuplicateKeys`) and on unstable normalization (`NormalizationIsNotStable`).
  - `GetLocalChanges()` (D2) reads only the local side: every non-excluded record whose hash differs from the state or is not in it (with its new hash), and every state record that is no longer local (hash null), except the missing files of a file adapter (they are taken again). An empty list means the planner cannot plan a push, so auto-sync asks the server nothing. Its errors are those of `CreatePlan`.
  - `Execute(plan, selection, progress, ct)` runs `RegistrySyncExecutor`. `RegistrySyncSelection` has `IncludePulls`, `IncludePullDeletes` (default true; D2's start-up pull sets false, so a record deleted on the server stays here and in the state until the manual sync; conflict resolutions are not affected), `IncludePushes` and `ConflictResolutions` (plan item → Local / Server / Skip; a missing item = Skip), with the presets `AllNonConflicting`, `PullOnly` and `PushOnly`, and `StopOnFailure` (C5): after the first Failed server operation the remaining server operations are NotExecuted, as after a transport error; the local operations still run, and a Conflict does not stop. The optional `progress` (`RegistrySyncProgress`: number, count, report item) runs after every executed server operation.
  - `RegistrySyncEngine.GetOperations(plan, selection)` returns `RegistrySyncOperations` (server items, local items) in execution order and runs nothing; `Execute` runs exactly these lists. A server item without a local side is a delete, a local item without a server side is a `RemoveLocal`.
  - Order: server upserts by ascending `Order`, then server deletes by descending order, then `ApplyLocal` ascending, then `RemoveLocal` descending, then one `IParametersManager.Save` of the root, only if local data or state changed. An engine with a `ServerAddress` writes it into `RegistrySyncState.ServerAddress` before that save; a new address is a change of the state.
  - A file adapter's `PrepareApplyLocal` runs right before its `ApplyLocal`. A failed preparation is `Failed` (no `ApplyLocal`, no state); after a transport error (of a server operation or of a preparation) the remaining preparations are NotExecuted and `TransportError` is set.
  - Each successful operation updates the record's state. After the local operations each touched adapter's local records are read again, and the state stores the hash of what the adapter now returns. A pulled record that does not show up, or a removed one that does not disappear, is `Failed` and gets no state, so the next sync cannot mistake it for a local delete.
  - A plan is executed once; build a new plan afterwards. Cancellation propagates without saving; the next run recovers, because equal content on both sides plans as InSync.
- **Server errors** (`RegistrySyncServerErrorCodes`, compared with `Error.Code`):
  - `ConcurrencyConflict` → outcome Conflict, and the rest continues.
  - `RecordWithNameNotFound` → Conflict on an upsert; on a delete the record is already gone, so the outcome is Done.
  - `ApiRequestFailed` → Failed, and every remaining server operation is NotExecuted. Completed operations stay in the state and the local operations still run.
  - Any other code (`RecordIsInUse`, validation, 5xx) → Failed, and the rest continues (unless `StopOnFailure`).
  - The first two are `nameof` B1's error factories in `SupportToolsServerApiClientErrors`; the adapters that check the version themselves (see below) create their errors with the same factories.
- **Report** (`RegistrySyncReport`): one `RegistrySyncReportItem(PlanItem, Outcome, Error)` per plan item, with outcome None, NotSelected, Done, Conflict, Failed or NotExecuted. It also has `TransportError`, `Changed` and `Saved`.

## Registry adapters (central registry)

`LibSupportToolsServerWork/Registry/Adapters/` holds one `IRegistrySyncAdapter` per shared collection (C3, C4 for Projects, C6 for StoredFiles), `Registry/Mappers/` the pure mappers. Tests: `SupportTools.Tests/Registry/Mappers/` (round trips, hash stability, Linux paths) and `Registry/Adapters/`, which run the real `SupportToolsServerApiClient` against `FakeSupportToolsServer`, an in-memory server with B1's version rules and the old git endpoints; `RegistrySyncAdaptersEndToEndTests` seeds it from a Windows computer and pulls everything to a Linux one through the engine. A DELETE starts the message hub, which writes to the console, so the adapter test classes are in `ConsoleCaptureCollection`.

- **Factory**: `RegistrySyncAdapterFactory.CreateAdapters(apiClient, parameters, pathMapper, warnings)` builds all of them; the caller (C5) creates the `PathMapper` from `parameters.PathMappings` and shows `pathMapper.Issues` and `RegistrySyncWarnings.Items` (collection, key or null, message; never a secret value). `RegistryCollections` holds the names (state keys, never rename) and orders: Environments 10, RunTimes 20, NpmPackages 30, ReactAppTemplates 40, DotnetTools 50, SmartSchemas 60, FileStorages 70, ApiClients 80, DatabaseServerConnections 90, Servers 100, GitIgnorePatterns 110, Gits 120, EditorConfigPatterns 130, ProjectTemplates 140, GlobalSettings 150, ProjectCreatorSettings 160, StoredFiles 165 (C6, see Registry stored files), Projects 170. The Projects adapter gets the Gits, NpmPackages, EditorConfigPatterns and DatabaseServerConnections adapters as `ProjectReferenceServerKeys`: every `RegistrySyncAdapter` exposes the keys of its last server read (`IRegistryServerKeys`), and the engine reads the adapters in `Order`, so Projects sees them already read.
- **Mappers** (`<X>Mapper`): `ToContract(key, local[, pathMapper])`, `ApplyToLocal(contract, existing[, pathMapper])` that sets only the contract's fields (or `ToLocal` for strings and the init-only `SmartSchema`), and `Normalize` (`ContractNormalization`: `EmptyToNull`, `OrderByName` for child lists, `EnumName` for the canonical spelling of enum names, `UpperDriveLetter` for canonical paths, because the real data holds `d:\` paths and a Linux `ToCanonical` gives back the rule's `D:\`; the rest of a path keeps its case). Required contract strings are not nulled. Machine fields stay out (`MachineLocalFieldsContractTests`).
- **Bases**:
  - `RegistrySyncAdapter<TContract>`: the casts and the server records. A key is left out on both sides (no push, pull or delete) when `IsSynced(key)` refuses it, or when `FindUnsupportedField` finds a server value this client cannot store (an unknown `EPeriodType`, `EDatabaseProvider` or `ESupportProjectType` name), which also adds a warning: uploading the local record would lose the server's value.
  - `DictionaryRegistrySyncAdapter<TLocal, TContract>`: `ApplyLocal` passes the existing record to `ToLocal`, which updates it in place.
  - `SingletonRegistrySyncAdapter<TContract>` (GlobalSettings, key `Global`; ProjectCreatorSettings, key `ProjectCreator`, B5's `RecordName`): an empty contract (hash of `new TContract()`) counts as missing on both sides, so a new computer pulls it without a conflict (the user's choice; SupportToolsServer's CLAUDE.md, Singletons, says the same). Delete writes an empty contract with the expected version, `RemoveLocal` clears the shared fields, and a create (expected version 0) over a server record that was emptied uses the version read with the plan.
  - `TemplateFilesRegistrySyncAdapter<TContract>` (GitIgnorePatterns, EditorConfigPatterns): a record is a list name plus the content of `{folder}\{name}.gitignore|.editorconfig`. A listed name without its file, or every name when the folder is not set, is left out on both sides with a warning. `ApplyLocal` writes the file (creating the folder) and adds the name; `RemoveLocal` only removes the name and keeps the file (the user's choice).
- **Old git endpoints** (Gits, GitIgnorePatterns, EditorConfigPatterns): B1 left `updategitrepo`, `syncup…/{merge}` and the old deletes without a version check, so `UpsertCheckingVersionOnClient` / `DeleteCheckingVersionOnClient` compare the version in the server's list first (B1's rule, with `ConcurrencyConflict` / `RecordWithNameNotFound`), write (a template goes as a one-row `SyncUp` with `merge=true`), and read the new version from the list. The old not-found codes (`GitWithKeyNotFound`, `…FileTypeWithNameNotFound`) become `RecordWithNameNotFound`. A change by another computer between the check and the write can still be overwritten (the user accepted that small window).
- **Collection rules**: DotnetTools sync only `PackageId`, `MaxVersion`, `Description`. ApiClients leave out the one named by `SupportToolsServerWebApiClientName` (bootstrap, G6) on both sides. Servers send no `IsLocal` and call `ServersIsLocalCalculator.Recalculate` after `ApplyLocal`. `FileStoragePath` is mapped only when it is a path (`PathMapper.IsWindowsRooted` or `FileStat.IsFileSchema`), not a URL. ProjectCreatorSettings map `ProjectsFolderPathReal` and `SecretsFolderPathReal` and create `AppProjectCreatorAllParameters` when it is null; so do the ProjectTemplates (its `Templates`). Gits normalize only the separators of `GitProjectFolderName`. DatabaseServerConnections replace the folders sets inside the existing dictionary.
- **Projects** (C4; `ProjectMapper`, `ServerInfoMapper`, `DatabaseParametersMapper`): one aggregate per project with its ServerInfos (G7). The 9 project paths and the two AppSettings files of a ServerInfo go through the `PathMapper`; `KeyGuidPart` travels (G2) and is never printed; `RouteClassModel.Version` is the contract's `ApiVersion`. Enum names (`EProjectType`, `EProjectTools`, `EProjectServerTools`, `EHttpMethod`, `EEndpointType`, `EDatabaseRecoveryModel`, `EBackupType`) unknown to this client make the server project `FindUnsupportedField`, so it stays out on both sides with a warning until SupportTools is updated (a pull would lose the name, a push would delete it on the server).
  - Removed ScaffoldSeeder mechanism: SupportToolsServer dropped its fields from the contract and the database (`ScaffoldSeederProjectName`, `ScaffoldSeederGitProjectNames`, `Seed…`, `PrepareProdCopyDatabase…`, `NewDataSeedingClassLibProjectName`, `ExcludesRulesParametersFilePath`, `DbContextProjectName`, `ProjectShortPrefix`, `MigrationSqlFilesFolder`, and `FakeHostProjectName` of the project creator settings). Its migration `RemoveScaffoldSeeder` also deleted the ScaffoldSeed gits and, from the project tool lists, the removed tool names and the numbers `7`–`10`, without new project versions, so a project that differed only in them plans as InSync. `ProjectMapper.Normalize` still drops the removed tool names (`JsonFromProjectDbProjectGetter`, `ScaffoldSeederCreator`, `SeedData`, `PrepareProdCopyDatabase`) and every number that is not an `EProjectTools` value (the local file stores `AllowToolsList` as numbers, 7–10 were the removed tools and stay in old files, and the remaining members keep their numbers), and `FindUnknownEnumField` accepts the removed names, so a project that still has them, in the local file or from a computer with an older SupportTools, keeps syncing.
  - ServerInfos: the natural key is (ServerName, EnvironmentName), ignoring case. `ApplyLocal` replaces the whole set (G7) inside the existing dictionary, keeps the local key (a GUID or `Server|Env`) of a record it finds by the natural key, gives a new one `"{ServerName}|{EnvironmentName}"` (a new GUID when another record holds that key) and removes the rest.
  - `ApplyLocal` updates the existing `ProjectModel` (and `ServerInfoModel`) in place when the contract changes none of its `init`-only fields (the database parameters only in content); otherwise it creates a new object that takes over the old one's lists, dictionaries and database parameters, and puts it into the dictionary (safe, because a pull runs before the menu is rebuilt). Every field of the aggregate is in the contract today; a new local-only field must be kept there too (`ProjectMapperTests.LocalModels_…` lists the fields the contract lacks).
  - Warnings (C5 shows them): a git, npm package, `.editorconfig` template or DB connection that is neither local nor among the server keys; a path without a canonical form; repeated values in a set, in the endpoint or route class names or in the ServerInfo natural keys, ignoring case. A project with repeated values is not sent: `Upsert` returns `RegistrySyncErrors.LocalRecordIsInvalid` (outcome Failed), while a pull still works. Local project keys that differ only by case are left out on both sides with a warning (`IsSynced`), so the engine does not stop the whole plan with `DuplicateKeys`.

## Registry sync command (central registry)

"Sync Registry With SupportToolsServer..." (C5) is the manual sync and, on the main computer, the seed of the server. It is in the main menu right after "Support Tools Server Editor"; the code is in `SupportTools/Menu/SyncRegistry/`, the tests in `SupportTools.Tests/Menu/SyncRegistry/`.

- **Flow** (`SyncRegistryCliMenuCommand`):
  - Connect with the ApiClient that `SupportToolsServerWebApiClientName` names, checked with one `GET environments`. A failure names the ApiClient and its address; a 401 (empty body, or ProblemDetails `Unauthorized`) asks to check its ApiKey; a transport error says the server does not answer.
  - Pre-flight (`RegistrySyncPreflight`): local keys that differ only by case, in any collection and Projects included, refuse the sync with a report (the user's choice). The Projects adapter's own exclusion stays for D2. A new collection adapter needs its keys in `GetLocalKeys` too; a test compares it with the factory.
  - `RegistrySyncSession`: the plan over all the factory adapters; the adapter warnings and `PathMapper.Issues` (warnings only, the user's choice); the summary per collection (`RegistrySyncPlanSummary`); then the choice menu.
- **Choices**:
  - Apply (non-conflicting pulls and pushes), Pull only, Push only; the menu shows how many records each one sends and changes here (`GetOperations`).
  - Resolve conflicts: Local / Server / Skip per conflict, with Show differences. Local wins for first sync conflicts is the group choice for the seed. The resolutions are kept by "collection/key" and run with their direction: Apply runs all of them, Pull only the Server ones, Push only the Local ones. The delete of a stored file is such a conflict ("deleted on the server, delete it here too?" / "deleted here, delete it on the server too?"), so it is the confirmation that C6 asks for.
  - Show details, Dry run (what Apply sends and changes here; nothing is sent), Exclude record from sync, Include excluded record again, Cancel.
  - Exclude adds the key to `ExcludedKeys`, saves and plans again. Include excluded record again (D4) lists the `ExcludedKeys` of the engine's collections (`RegistrySyncEngine.CollectionNames`), removes the chosen key, saves and plans again; it is offered only while such a key exists.
  - When nothing is left to sync, the plan is still executed, so a first sync records the state of the equal records. While excluded keys exist, the session asks first with only Finish (records the state) and Include excluded record again, so a record can be put back even when nothing else differs.
- **One collection** (D4): `SyncRegistryCliMenuCommand.ForCollection(…, RegistryCollections.X)` is the same command over that adapter only (name `Sync X With SupportToolsServer...`, the pre-flight checks only that collection). The `Gits`, `GitIgnorePatterns` and `EditorConfigPatterns` list menus (`GitCruder`, `GitIgnoreModelsCruder`, `EditorConfigPatternsCruder`) offer it in place of the old Merge/Sync Up/Down commands, which D4 deleted (the user's choice: one sync semantics). A git whose `.gitignore` template is not on the server fails on the server (404), so sync the templates first.
- **Execution**: the selection always has `StopOnFailure` (the user's choice), so hundreds of seed requests stop at the first rejected record. Every executed server operation prints `n/count op Collection/Key: outcome`. The report counts the outcomes, names the conflicts and failures and where the sync stopped, and after a pull names the `.bak` copy that `ParametersManager.Save` (A4) made, so the command makes no copy of its own. Then the menu reloads (`EMenuAction.Reload`).
- **With auto-sync (D2)**: the command saves through `AutoSyncParametersManager.WithoutAutoSync(...)`, so its own saves (the execution, Exclude record) never auto-push: the user chose what to send (e.g. Pull only). Its engine has the address of the ApiClient, so every execution records `RegistrySyncState.ServerAddress`; this is how a computer moves auto-sync to a new server (Cancel records nothing).
- **Secrets**:

## Registry stored files (central registry)

`StoredFilesRegistrySyncAdapter` (C6; collection `StoredFiles`, Order 165, right before Projects) syncs the secret files that the registry points to through B8's `files` endpoints; the C5 command uses it like any adapter of the factory. Tests: `SupportTools.Tests/Registry/Adapters/StoredFilesRegistrySyncAdapterTests.cs`, `StoredFilesSyncEndToEndTests.cs` (two computers; the Linux one uses forward-slash temp paths, so Windows can write them) and, for the engine, `Registry/Sync/RegistrySyncEngineFileAdapterTests.cs` with `FakeFileRegistrySyncAdapter`.

- **Which files** (the user's choice): every `ServerInfo.AppSettingsJsonSourceFileName` and the project's `PairedDbObjectsResultFileName`; not the generated `AppSettingsEncodedJsonFileName` and not the rest of `SecurityFolder`. A file inside a git working tree (a `.git` folder or file in any parent folder) is left out on both sides without a warning: git carries it (12 of the real appsettings files are tracked in repos).
- **Key and paths**: the key is `UpperDriveLetter(PathMapper.ToCanonical(registry path))`; the file of a key is `PathMapper.ToLocal(key)`, and a pull creates the missing folders. Keys that differ only by case are merged (one file on Windows), so the preflight leaves StoredFiles out. A key that B8's path rule refuses (`StoredFilePathRules`: `X:\…` with `\` only, no empty segment or one that ends with `.` or a space, no `<>:"/|?*`, at most 400 characters) or that has no form on this computer (a `ToLocal` issue of the `PathMapper`, or a path that is not fully qualified on this OS) is left out on both sides with a warning.
- **Contract** (`StoredFileContract`, client-side, because the server list has no content): `Sha256` and `Length` of the UTF-8 bytes without the BOM, exactly B8's `StoredFile.ComputeSha256` rule, plus the server `Version`; `Path` is `[JsonIgnore]`, so a case-only spelling difference is no change. `LocalStoredFile` reads only UTF-8 text up to `StsStoredFileDataModel.ContentMaxBytes` (1 MiB, the BOM not counted); a larger file, one with a NUL byte or invalid UTF-8, or an unreadable one is left out on both sides with a warning. Writing keeps the BOM of an existing file; a new file has none.
- **Local records** (file-based deletion, the user's choice): an existing, readable file whose key the registry points to, the server has, or the sync state holds. A file therefore stays in the sync while it exists, even when the registry no longer points to it. `GetMissingLocalKeys` gives the registry keys whose file is missing: they are taken again and never deleted on the server. So a server delete is offered only when the local file is gone and nothing points to it, and every delete, in either direction, is a `DeleteNeedsConfirmation` conflict (Local: delete on the server, or upload again; Server: delete here, or take again). `RemoveLocal` deletes the file; when that fails, a warning gives the reason and the engine reports the record as Failed.
- **Content**: `GET files` gives metadata only. `PrepareApplyLocal` downloads the content of a pulled file (`GET files/content`), and `ApplyLocal` writes it; it throws when nothing was prepared and lets write errors through, because an old file would otherwise look pulled and never be updated. `Upsert` reads the file at push time: a file changed since the plan sends its new content (the next plan finds both sides equal), and an unreadable one returns `LocalRecordIsInvalid`. The content never reaches the console, a log or a diff (`RegistryRecordDiff`: `Length` and 8 characters of `Sha256`).
- **Manual check** (after C5's): on PAZISI run the sync. The seed adds about 26 StoredFiles records (21 appsettings files under `D:\1WorkSecurity` and 5 `PairedDbObjectsResults` under `D:\ProgData`); compare them with `GET files`. ## Registry auto-sync (central registry, D2)

Auto-sync runs the engine with the factory adapters at two moments: at the start (Pull) and after every save (Push). It is opt-in per computer: `AutoSyncWithSupportToolsServer` (default false) and `SupportToolsServerSyncTimeoutSeconds` (default 10) are machine fields (`MachineLocalFields`), edited in "Support Tools Parameters Editor" right after `SupportToolsServerWebApiClientName`. The manual command (C5) stays for conflicts and the rest. Code: `SupportTools/AutoSync/`; tests: `SupportTools.Tests/AutoSync/`.

- **Registration** (`SupportToolsServices`): ParametersManagement's `AddMainParametersManager<T>` needs `T : ParametersManager`, so it is not used: `Configure<MainParametersManagerOptions>`, `AddSingleton<SupportToolsMainParametersManager>()`, `AddSingleton<RegistryAutoSync>()` and `AddSingleton<IParametersManager, AutoSyncParametersManager>()`. The decorator is the only `IParametersManager`, so the menu and `--run` (`ProjectToolRunner`) save through it; `RegistryAutoSync`'s public constructor takes `SupportToolsMainParametersManager`, the inner manager. `SupportToolsServicesTests` checks this.
- **Decorator** (`AutoSyncParametersManager`): `Parameters` and `ParametersFileName` are the inner manager's (same object, so the ~150 casts are unchanged). `Save` saves locally first; only after a successful save it calls `RegistryAutoSync.PushAfterSave`, and it always returns the local result: a server error never spoils the save. `WithoutAutoSync(manager)` returns the inner manager (C5 uses it).
- **No recursion**: the engine of auto-sync gets the inner manager, so its state save does not go through the decorator.
- **Start** (`RegistryAutoSync.PullOnStart`, called by `Program.cs` after the parameters load and `ServersIsLocalCalculator`, before the menu and `--run`): plan, then only the non-conflicting pulls without deletions (`IncludePullDeletes = false`, the user's choice: an empty or wrong server must never wipe the local registry silently). One summary line: `Registry auto-sync: 3 records taken from SupportToolsServer` or `nothing new on SupportToolsServer`; when records wait (to send, deleted on the server, in conflict, not taken, adapter warnings) the line becomes a warning that ends with `; run "Sync Registry With SupportToolsServer..." for …`. `CliAppLoop.Run` (AppCliTools) clears the screen first, so in menu mode `PullOnStart(deferOutput: true)` keeps its output and `SupportToolsMenuBuilder.BuildMainMenu` writes it once (`WriteDeferredOutput`), under the header of the first main menu; with `--run` it is written at once.
- **After a save** (`PushAfterSave`): `GetLocalChanges` first, without the server. No change → no request. That covers the 2–3 saves of one operation (ParCruder + Cruder): with the real adapters one changed save costs one plan (18 GETs) and its POSTs, and the next saves cost nothing. The same set of changes as the last attempt (a conflict that waits, a rejected record) is not tried again until the local changes change. Otherwise plan and `PushOnly`: `sent to SupportToolsServer: <names>`; conflicts (of the plan, or a 409/404 at the push) leave the local change waiting with a warning to run the manual sync; a rejected record names the server's error.
- **Guards**:
  - Server address: when `RegistrySyncState.ServerAddress` is set and differs from the ApiClient's address (ignoring case, a trailing `/` and edge spaces), auto-sync does nothing and warns (the user's choice: the state of another server would plan deletions); one manual sync with the new server records its address. An empty address (a file older than D2) is accepted and written by the first execution.
  - Offline: a transport error (`ApiRequestFailed`) or a request longer than the timeout (`TimeoutHttpClientFactory` sets `HttpClient.Timeout` per request, which `ApiClient` turns into `ApiRequestFailed`; a large first pull is not cut off) warns once and suspends auto-sync until SupportTools restarts (the user's choice), at the start as after a save. The program goes on with the local copy.
  - A missing ApiClient name, ApiClient or address is a warning, shown again only when it changes. Any exception is caught and shown as a warning.
- **Secrets**: the API client is created without the console; the output names records (`Collection/Key`) and server error descriptions, never field values or the API key.
- **Tests**: `RegistryAutoSyncTests` (start-up pull, guards, timeout), `AutoSyncParametersManagerTests` (the decorator: push after a successful save, no push after a failed one, offline, conflicts, auto-sync off, no recursion, repeated saves), both over `FakeRegistrySyncAdapter` (`AutoSyncTestContext`); `RegistryAutoSyncEndToEndTests` (two computers with the real adapters, the real `ParametersManager` and `FakeSupportToolsServer`); `RegistrySyncEngineGetLocalChangesTests`; `SupportToolsMenuBuilderTests` (the deferred summary); `ProgramTests` (the real entry point `Program.<Main>$` in this process, `--run` mode only: the pull warns before the tool; the menu mode needs a real console).
- **Manual check** (after C5's and D1; the tests never reach a real server):
  1. On both computers: the bootstrap ApiClient points to the same SupportToolsServer, run the manual sync once (it records the server address), then turn on `AutoSyncWithSupportToolsServer`.
  2. Computer A: change a record (e.g. the description of an environment or a project field) and save. The line `Registry auto-sync: sent to SupportToolsServer: Environments/<name>` appears; a second save of the same data prints nothing.
  3. Computer B: start SupportTools. Under the SupportTools header, above the main menu: `Registry auto-sync: 1 record taken from SupportToolsServer` (a warning line when something else waits), and the change is in the menu. With `--run` the line comes right after `Loading...`.
  4. Conflict: with SupportTools open on both computers, change a record on A and save (it is sent), then change the same record on B and save. B warns `the local changes of <Collection>/<Key> (changed here and on the server) wait: run "Sync Registry With SupportToolsServer..."`; B's next start counts it as in conflict, and the manual sync resolves it.
  5. Offline: stop the server or point the ApiClient to a wrong port, start SupportTools: one warning after at most the timeout, then the menu works as before and saves make no requests.

## Git sync V3 (remote heads from SupportToolsServer)

"Sync All Projects All Gits V3", "Sync One Group All Projects Gits V3" and "Sync One Project All Gits V3" (each right after its V2 command in `MenuData`; `SupportTools/Menu/...CliMenuCommandV3`) run `LibGitWork/ToolActions/SyncMultipleProjectsGitsToolActionV3`: V2's work (clone, `rm --cached` of the files `.gitignore` excludes, `add .`, commit, pull, push), faster. V2 and its other callers (Update Outdated Packages, Clone Project To This Computer) are unchanged. "Distribute all packages" syncs each package project through V3 (`PackageDistributionSteps`) with a commit message it makes itself, so it never asks: the first sync names the packages of this run that the project uses (`Distribute all packages: use new Core, Util packages in Alpha`, or `… before Alpha package` when there are none), the final one is `… after Alpha package`; the remote-only question (D3) is the same. Right before that first sync a package project takes the packages of this run that it uses, and after the last package the projects that are not packages (`UseLocalPackages` on) take theirs, uncommitted; a failed one does not stop the others (the user's choice). A package project whose step fails (after the error's `press any key...`) is skipped, and so is every package project that uses a failed or skipped one (it is not built with the old version); the others go on, and the run ends with `finished with errors … Failed: …` (the user's choice). `PackageDistributor.DistributePackagesToProject` first pulls every clean copy of those package gits next to the project and only then raises the versions and swaps the references package by package: a restore that sees a pulled copy next to one that is still old fails with NU1605 (the old copy pins a package directly and references the pulled one as source). The single "Package distribution" command still distributes one package to all its consumers. `PackageBuilder` (Build Package, and each package of the run) packs the whole solution, which also lists projects of the clones of other repositories next to it (`../SystemTools/...`), but uploads only the packages of the projects in the solution folder: an uploaded copy would be the latest version of that package on the server, which the distribution takes, and some copies depend on versions that are never uploaded (NU1102). A package that depends on a package of its own version that it does not upload (a project reference to another repository) stops the upload. A package project that has not changed since its last upload is not built again (`DistributeAllPackages/UploadedPackageChecker`, right after its first sync; nothing is stored locally): SourceLink writes the commit a package was packed from into its nuspec (`<repository commit>`), so when every package of the repository that the server has (`PackageBuilder.GetOwnProjectNames`, the csproj names under the solution folder; a 404 is no package) has the same newest version, the nuspec of the first one names the repository's HEAD and `git status` is clean, the project gets only its solution check (it also keeps this computer's NuGet source mapping) and skips the build check, the pack, the upload and the final sync. Its packages still count as packages of this run, so the projects that use them take them as before (an earlier, stopped run may have uploaded them without distributing them). Anything else, a git or server error too, builds as before; a package uploaded from the other computer counts as well. Code: `LibGitWork/SyncV3/`; tests: `SupportTools.Tests/SyncV3/`, `ToolActions/SyncMultipleProjectsGitsToolActionV3Tests.cs` and the three menu `...V3Tests`.

- **Folders**: as V2 (projects in name order, the gits of each, `GitSyncParameters.Create` for the path), each path once. Then each git's work-folder clone (`WorkFolder\Gits`, the folder of V2's `GitProjectsUpdater`) as the last folder of its git, so it takes the pushes and V2 has nothing to pull afterwards: synced like the others but never changed (no `rm --cached`, no `add .`; local changes are an error, because V2 offers to restore them) and not scanned for projects. Without `WorkFolder`: a warning and no work-folder clones.
- **Remote heads**: one `GET git/gitremoteheads` through `SupportToolsServerWebApiClientName` (no names for every project, which keeps the address short; the names of its gits for a group or a project, so the server checks only those), started before the local check and awaited after it. SupportToolsServer caches each head 10 minutes (its CLAUDE.md, Git remote heads). No ApiClient name, a missing ApiClient or an error → one warning and every git is fetched (V2's behaviour without the work clone).
- **Local check** (`GitFolderInspection.Inspect`, `Parallel.For`, `MaxParallelism` 8, the user's choice: a constant): missing folder → clone later; else `config --get remote.origin.url` must equal the git's address, then `ls-files -i --exclude-from=.gitignore -c` + `rm --cached`, one `status --porcelain=v2 --branch --untracked-files=normal` (`GitFolderStatus`: HEAD, `origin/<branch>` upstream, tracking ref equal or not, changes), `add .` when changed.
- **Questions** before the parallel part: V2's commit message rule (`Message`, then `Use this message for next commits?`, asked per changed folder until kept; not asked after the last folder). The internal constructor takes the inputs, the `IHttpClientFactory` and the `IProgressConsole`.
- **Sync** (`GitRepositorySyncer`, one per git, `Parallel.ForAsync` 8 gits at a time; the folders of a git in order, changed ones first): commit; then a folder is **skipped without any request** when it has no changes, its upstream is `origin/<server branch>` and HEAD is the known commit (a stale tracking ref is moved there with `update-ref`, as a fetch would); otherwise `remote update` and V2's state loop on `rev-parse @`, `@{u}`, `merge-base`: NeedToPull → `merge --ff-only @{u}` (no second fetch), Diverged → `pull`, NeedToPush → `push` (a rejected push: one more `remote update` and the loop again). A branch without any upstream (made here and never pushed, e.g. a session's feature branch) is published after the `remote update` with `push --set-upstream origin <branch>` instead of the loop (the user's choice; V2 stops it with `Unknown state`): it counts as pushed and its line says `published branch <name>`. A remote branch of that name with commits this one lacks rejects it (a red line; `git branch -u origin/<branch>` and sync again). A detached HEAD still fails with `has no upstream branch`, and an upstream of another remote is synced as before. The known head starts as the server's and becomes `@{u}` after every synced folder of that branch, so without the server only the first folder of a git fetches. Folders processed before the last push of their git are synced once more. After a push `POST git/gitpushed/{git}`; a refused notification is a red line, not a failure.
- **git**: `GitFolderCommands` passes arguments through `ArgumentList`, captures stdout/stderr (never the console), sets `GIT_TERMINAL_PROMPT=0` and `GIT_MERGE_AUTOEDIT=no` and closes stdin, so git never waits for input (a password prompt fails instead).
- **Console** (`ParallelProgressBoard`): a header and one line per running job at the bottom, updated in place under a lock; permanent lines (`WriteLine`: changes found, `cloned/committed/pulled/pushed`, errors in red) above it. Lines are cut to `WindowWidth - 1`, so the board's top is always `CursorTop - renderedLines`, also after the screen scrolls. `Console.IsOutputRedirected` → no board (`IProgressConsole` null), only the permanent lines. Tests use `FakeProgressConsole` (a screen with scrolling); a real Windows Terminal was checked with a scratch harness.
- **Output**: `Checked N folders: …`, `Remote heads from SupportToolsServer: X of Y gits` (+ `Checked with fetch: …`), then `Synced N gits, M folders: K without a request to the git server, … fetched, … cloned, … committed, … pulled, … pushed, … failed`. `Run` returns false when a folder failed.
- **Manual check** (after the server part): run V2's "Sync All Projects All Gits" and V3's on the same data and compare the time and the summary; run V3 again within 10 minutes: every clean folder should be `without a request`. Push a commit from another computer through V3: the next V3 run here pulls it (the server was notified). Stop the server: V3 warns and fetches every git.

## Server installations (Ubuntu autoinstall USB)

"Server Installations" (main menu right after BaGetter) is a `CruderListCliMenuCommand` over `ServerInstallationCruder` (`SupportToolsParameters.ServerInstallations`, a machine-local field: the registry has no such collection and the records hold password hashes). Each record (`ServerInstallationModel`) generates the `grub.cfg` and `autoinstall.yaml` of an Ubuntu Server installation USB (Rufus, "ISO Image mode"); the model files are the ones in `D:\1Work\oslo` that installed the oslo server. Code: `SupportTools/Menu/ServerInstallations/`; tests: `SupportTools.Tests/Menu/ServerInstallations/`.

- **Passwords**: never stored. `PasswordHashFieldEditor` asks twice and stores only the hash: Linux SHA-512 crypt (`$6$`, checked against openssl), MariaDB `*SHA1(SHA1)`, SQL Server `0x0200` + salt + SHA-512 of UTF-16LE (both checked against the real oslo hashes).
- **Disk and network**: the disk is `storage.layout` `direct` with `match: serial` (udev `ID_SERIAL`, the user's choice), so another computer fails before anything is erased; the partition sizes are subiquity's. "Read Disk And Network From autoinstall-user-data..." takes the serials (`storage.config`, `type: disk`) and the ethernet names from a copy of `/var/log/installer/autoinstall-user-data` (`AutoinstallUserDataReader`, YamlDotNet) and asks when there are several. No IPv4 addresses → `dhcp4: true`. Bonds (riga: `bond0` of `eno1`–`eno4`, `balance-rr`): with `BondInterfaceNames` set, `NetworkInterfaceName` is the bond, which gets the addresses under `network.bonds` (plus `parameters.mode` when `BondMode` is set, validated against netplan's modes), and each member is an empty `ethernets` entry; the reader offers a bond as one interface (its members are not offered) and takes its members and mode, and choosing a plain ethernet clears them. Without a bond the output is unchanged (oslo's file is byte-identical).
- **Apps** (`~/install-apps.sh`, run by hand after the first boot, re-runnable): curl first (when missing), then Virtualmin (`--bundle` from `Bundle`: `LampApache` → `LAMP`, `LempNginx` → `LEMP`, the default and the old fixed value; it brings Webmin and MariaDB and answers the Post-Installation Wizard; needs `DomainName` for the FQDN), else Webmin and PostgreSQL through apt; there is no `InstallMariaDb` (the user's choice: MariaDB comes only with Virtualmin), and its root hash is set on every run; SQL Server always installs sqlcmd (it sets the sa hash). `SqlServerPort` other than 0 and 1433 (the default) moves SQL Server to that port, only when `mssql.conf` does not have it yet (`mssql-conf` refuses a port in use, which broke re-runs); `OpenSqlServerPort` opens the listened port in firewalld when it runs (Virtualmin sets it up), else in the `profile_hosting_tcp_ports` set of Webmin's `inet webmin_profile_hosting` table when it exists (live `nft add element` plus its `elements` line in `/etc/nftables.conf`: that table's input chain has `policy drop`, so an accept rule in another table opens nothing, as on oslo), else in `/etc/nftables.conf` (the user's choice). The Service Install Script Creator opens the Kestrel ports of the project's appsettings the same way. `InstallDotnetSdk` (`dotnet-sdk-10.0`) or, without it, `InstallDotnetRuntime` (`aspnetcore-runtime-10.0`) come from Ubuntu 26.04's own feed (Microsoft's install page for 26.04); an apt pin (`/etc/apt/preferences.d/dotnet-not-from-microsoft`) keeps the Microsoft repository of sqlcmd / SQL Server from supplying .NET packages (Microsoft's package mix-up page). `Validate` lists every error at once; values that reach shell or perl are limited to safe characters (the regexes end with `\z`, so a trailing line feed fails too), and an IPv4 value must be written exactly as `IPAddress.ToString` gives it (`192.168.10` is refused). The console input of the field editor and the commands goes through internal constructors, as in the rest of the menu.
- **Files**: "Generate grub.cfg And autoinstall.yaml" writes them (LF, no BOM) to `FilesFolder` or `{WorkFolder}\ServerInstallations\{name}`. "Write To Installation USB..." lists the ready drives with `boot\grub\grub.cfg` and `casper`, in an RDP session (`SESSIONNAME` `RDP-…`) also the client's redirected drives `\\tsclient\A\`–`Z\` (the user picks one and confirms), keeps the ISO's file once as `boot\grub\grub.cfg.original`, and writes `boot\grub\grub.cfg` and `\autoinstall.yaml`.
- **Not checked on hardware**: the layout `match`, the LAMP bundle, the Webmin-only, apt-only and port branches of the script. With the oslo parameters the output differs from the oslo file only in quoting, comments, the storage section and the place of the MariaDB step.

## Service ports (ServerInfo.OpenPort)

`ServerInfoModel.OpenPort` (Yes/No, services only; synced through the registry contract `StsServerInfoDataModel.OpenPort`, server migration `AddServerInfoOpenPort`) opens the service's ports in the server's firewall. The ports are the Kestrel `Endpoints:*:Url` ports of `AppSettingsJsonSourceFileName` (`LibAppInstallWork/KestrelPortsReader`; `GetPortsToOpen` gives an empty list when OpenPort is off and an error when it is on and no port is found). `OpenPortFieldEditor` shows the port (or why it is unknown) in its prompt and status.

- Service Install Script Creator: the script's `open_port` (firewalld, else Webmin's `profile_hosting_tcp_ports` set, else an `inet filter` rule) runs only for those ports.
- Program Installer and Program Updater (service projects, `ServiceUpdaterToolCommand`): the ports go through `InstallServiceAction` → `IIProjectsManagerWithFileStorage.InstallService(…, portsToOpen)` → locally `ApplicationUpdater` / `InstallerBase.RunUpdateService`, remotely `ProjectsApiClient` (`UpdateServiceRequest.PortsToOpen`) → WebAgent's `UpdateServiceCommandHandler` (WebAgentShared). `InstallerBase` opens them before the service starts: `LinuxServiceInstaller` the same way as the script (`NftablesConf` edits the set's `elements` in `/etc/nftables.conf`), `WindowsServiceInstaller` with a `netsh advfirewall` rule `"{service} port {port}"`. An old WebAgent ignores `PortsToOpen`.
- ToolsManagement.Installer consumes `WebAgentContracts.WebAgentProjectsApiContracts` as a BaGetter package, so a change of `ProjectsApiClient` builds only after the new WebAgentContracts package is distributed.

## Database scope (IsDbTools, UsesDatabase)

`EProjectType.IsDbTools` (3) is a project of database tools; `ProjectModel.UsesDatabase` (default true, so old files and new projects keep everything) turns the database part of a project off. The rules are in `SupportToolsData/ProjectDatabaseScope` (`IsDbTools`, `ShowsDatabase`, `IsToolVisible`, `IsDatabaseTool`, whose switches throw for an unclassified tool, so a new `EProjectTools` / `EProjectServerTools` member must be classified there).

- IsDbTools: the project editor (`ProjectCruder.CheckFieldsEnables`) hides the application fields (versions, web agent, masks, security folder, main/api contracts/SPA project names, AppSetEnKeys, KeyGuidPart, UsesDatabase, endpoints, route classes, npm packages) and keeps the general and the database ones; the servers (`ServerInfoCruder`) show only the server, the environment and the database parameters; only the database tools are offered. `UsesDatabase` is ignored.
- UsesDatabase off: the database fields of the project (`DevDatabaseParameters` … `PairedDbObjectsResultFileName`) and of its servers, the Paired Db Objects menu and the database tools are hidden.
- Tools: "Select Allow tools..." (project and server) lists only the visible tools and leaves the choices of the hidden ones as they are; the tools lists and `--run` (`ProjectToolRunner`) offer only allowed tools that are also visible. Nothing is deleted from the parameters.
- Registry: `StsProjectDataModel.UsesDatabase` is `[DefaultValue(true)]` with a `true` initializer, so the hash omits true (existing hashes stay) and a client or server that does not know the field reads true. Server: `Project.UsesDatabase`, column default and sentinel true, migration `AddProjectUsesDatabase` (SupportToolsServerDbTools).

## Conventions to match

- Code comments are predominantly in Georgian — match the language of nearby comments rather than translating.
- Use `StShared.WriteException` / `StShared.WriteErrorLine` (from `SystemTools.SystemToolsShared`) for diagnostics rather than `Console.WriteLine`.
- `Serilog` is the configured logger; logs land under the parameters-file `LogFolder`.
- Local-vs-remote routing on a `ServerDataModel` is controlled by `IsLocal`. Remote = HTTP to WebAgent.

## What not to touch without good reason

- `Directory.Build.props` / `Directory.Packages.props` — global; affects every project.
- The strategy auto-registration calls in `SupportToolsServices.cs` — `AddTransientAllStrategies` uses `Assembly` markers; one marker per assembly is sufficient and adding another won't help.
- `.editorconfig` — 16 KB of enforced rules. If a rule is "wrong," prefer a local `// ReSharper disable once` over editing the file.
